- **發生什麼**：10/7 Anthropic 發布 Claude Haiku 5.5，$0.10／$0.50 per Mtok（prompt 超過 100K 時 $0.50／$2.50），1M context，第一個可以調 effort 的 Haiku。Claude Code 2.1.293 起它是預設 Haiku。同時 Sonnet 5.5 的 cache read 從 $0.20 降到 $0.10/Mtok，Claude Code 2.1.296 的 `/cost` 與 `--max-budget-usd` 已改用新價計算。

- **來源**：[早報 10/9 §3](../daily/2026-10-09.md)、[Haiku 5.5 官方頁面](https://www.anthropic.com/claude-haiku-5-5)、[Claude Code CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

### ② Claude Code hooks 可以 fail-closed 了，而且「用自然語言寫的 hook 會放行」的 bug 被修掉

- **發生什麼**：2.1.294 修正 `prompt`／`agent` hook 用指令語氣寫（例如「Block commands that…」）時反而放行的問題；2.1.295 新增 command／HTTP hook 的 `onFailure: "block"`，hook 啟動失敗、逾時、回傳非預期 exit code 或無效輸出時擋下動作，不再默默放行。本週稍晚的 2.1.296（發布日期待確認）又修了 managed settings 裡 `PreToolUse` hook 擋下後沒結束 turn 的問題，並讓 `--debug` 記錄每個 command hook 的指令、結果與耗時。
- **為什麼重要**：這代表 hook 終於可以當「護欄」用，而不只是「建議」。但也提醒一件事：你以為在擋的 hook，可能從來沒擋過。本週深度主題就是這個。
- **我該做什麼**：盤點你寫過的 hook，安全類規則改用 command hook ＋ `onFailure: "block"`，並且**實際餵一個該被擋的輸入測一次**。注意 `onFailure` 對 Stop／SubagentStop 無效（見深度主題）。
- **來源**：[早報 10/9 §1](../daily/2026-10-09.md)、[Hooks reference](https://code.claude.com/docs/en/hooks)、[CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)

### ③ 「coordinator agent 只規劃、不寫 code」成為各家共同形狀

- **發生什麼**：Cursor 10/6 推出 Projects，由 coordinator agent 規劃、分派給子 agent，最後把成果交回給人驗收，還能排定週期性工作；Haiku 5.5 公告提到 Cognition 的 Devin CLI 用 Opus 5.5 當 lead、Haiku 5.5 當 subagent；OpenAI Codex 桌面 app 讓你選擇跑到一半補充的指令要「立即轉向」還是「等下一輪」。

## 3. 🔬 深度主題：用測試與 Hooks 驗證 AI 產出

### 3.1 背景：為什麼「請 Claude 記得跑測試」不夠

你在 CLAUDE.md 寫「改完請跑 `npm test`」，前幾個任務它都會照做；對話一長、經過 compaction，或任務很多步時，這條規則就會被稀釋。社群把這種情況叫做 **Verification Gap**：agent 在測試確認之前就宣告完成（[cc.bruniaux.com 的 TDD 指南](https://cc.bruniaux.com/guide/workflows/tdd-with-claude/)，社群文章）。

解法是分三層：

| 層 | 放什麼 | 性質 |
|---|---|---|
| CLAUDE.md / Skills | 「為什麼」與流程：先寫測試、改完 build | 建議，Claude 可能忘 |
| **測試** | 「什麼叫做對」：可執行的規格 | 確定性，但要有人跑 |
| **Hooks** | 「一定要跑」與「絕對不准」 | 確定性，由 harness 執行，不靠 Claude 自覺 |

測試是規格，hook 是執行規格的機制。兩者缺一，驗證就會有洞。

### 3.2 運作原理：hook 怎麼「擋」

以下整理自官方 [Hooks reference](https://code.claude.com/docs/en/hooks)（本週讀取的版本）。

**事件**：跟驗證最相關的是四個：

- `PreToolUse`：工具執行**前**，可以擋（適合「絕對不准」：不准改 `dist/`、不准 `git push --force`）
- `PostToolUse`：工具成功**後**，已經做了不能擋，只能把訊息回饋給 Claude（適合「改完馬上 lint／跑相關測試」）
- `Stop`／`SubagentStop`：Claude（或 subagent）**要結束回覆時**，可以叫它繼續做（適合「測試沒過不准說完成」）

**hook 類型**：`command`（跑 shell 指令）、`http`、`mcp_tool`、`prompt`（單次 LLM 判斷）、`agent`（可以用工具的 subagent 驗證，官方標示 experimental，正式流程建議用 command hook）。

**command hook 的 exit code 是重點**：

| exit code | 意義 |
|---|---|
| `0` | 成功。stdout 若是 `{…}` 會當 JSON 解析；stderr 不會給 Claude 看 |
| `2` | **擋下**。stderr 是理由，會回饋給 Claude；就算同時印了 JSON 也照樣擋 |
| 其他（例如 1） | **非阻擋錯誤，動作照常進行**。官方原文：「If your hook is meant to enforce a policy, use `exit 2`.」 |

最常見的陷阱：腳本寫 `process.exit(1)` 或 `throw`，以為擋了，其實放行。

**exit 2 在不同事件的效果不一樣**：`PreToolUse` 擋下工具呼叫；`Stop` 是「阻止 Claude 停下、繼續對話」；`PostToolUse` 只把 stderr 給 Claude 看（工具已經跑完）。

**JSON 輸出**（exit 0 時）可以做更細的控制，例如 `PreToolUse` 回傳：

```json
{
  "hookSpecificOutput": {
    "hookEventName": "PreToolUse",
    "permissionDecision": "deny",
    "permissionDecisionReason": "dist/ 由 npm run build 產生，請改 src/"
  }
}
```

`permissionDecision` 可以是 `allow`、`deny`、`ask`（跳出確認給你）、`defer`。`ask` 很適合「改測試檔要人看過」這種規則。

**`onFailure`（2.1.295+）**：只能設在 `command`／`http` hook，`"continue"`（預設）或 `"block"`。hook 無法啟動、exit code 不是 0 或 2、HTTP 錯誤、逾時、輸出無效，都算失敗；設成 `block` 時失敗等同 exit 2。**它對 Stop、SubagentStop、TaskCompleted、TeammateIdle 和背景 hook 沒有效果**。換句話說，10/9 早報練習裡「在 Stop hook 加 `onFailure: "block"`」那一步其實不會生效，fail-closed 要放在 `PreToolUse` 這類事件上才有意義（在此更正）。

**Stop hook 的無限迴圈保護**：

- 輸入裡有 `stop_hook_active`，當 Claude 已經是因為 stop hook 而繼續時為 `true`，你的腳本應該檢查它，避免卡在永遠無法滿足的條件。
- Claude Code 有 **8 次連續續跑上限**：stop hook 連續擋 8 次後，第 9 次會被強制放行；只要 Claude 中間呼叫過工具，計數就歸零。可用 `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` 調整。

**prompt hook** 回傳 `{"ok": true}` 或 `{"ok": false, "reason": "…"}`；在 Stop 上，`ok: false` 會把 reason 當成下一個指令讓 Claude 繼續，另外可以回 `impossible: true` 表示條件不可能達成，直接放行。`PreToolUse` 上預設會結束 turn，要設 `continueOnBlock: true` 才會把理由回給 Claude 讓它修正。

**matcher**：只含字母、數字、`_ - , |` 和空白時是精確比對（`Edit|Write`）；其他字元會被當成**未錨定**的 JavaScript regex，需要整串比對時要自己加 `^…$`。另外 handler 上的 `if` 欄位可以用權限規則語法，例如 `"Bash(git push *)"`。

**設定位置**：`~/.claude/settings.json`（全部專案）、`.claude/settings.json`（專案，進版控）、`.claude/settings.local.json`（專案，不進版控），各層會**合併**而不是覆蓋；subagent 和 skill 的 frontmatter 也能帶 hook。預設 timeout：command 600 秒、prompt 30 秒、agent 60 秒。

**除錯**：`claude --debug` 會把 hook 執行紀錄寫到 `~/.claude/debug/<session-id>.txt`（不會印在終端機），2.1.296 起還會記錄每個 command hook 的指令、結果與耗時。

**安全**：互動模式下，專案的 hook 要等你接受 workspace trust 才會執行；但 `claude -p` 和 SDK **不會跳 trust 對話框，直接當作信任**，所以對陌生 repo 跑 headless 前，要先看 `.claude/`，或加 `--settings '{"disableAllHooks": true}'`。

### 3.3 該用哪一種：優缺點與適用情境

| 方式 | 優點 | 缺點 | 適合 |
|---|---|---|---|
| command hook + exit 2 | 確定性、快、可以單獨測 | 只能檢查寫得出程式的規則 | 檔案路徑規則、跑測試、比對產物 |
| command hook + `onFailure: "block"` | 腳本壞掉也不會變成沒防護 | 腳本一壞就卡住所有相關動作 | 安全類規則（不准改 `.env`、不准 force push） |
| prompt hook | 能判斷語意（「這個 commit 訊息有沒有說明原因」） | 非確定性、多花 token、曾有放行 bug | 確定性規則寫不出來時的補充，**要準備正反例測試** |
| agent hook | 可以讀檔、跑指令再判斷 | experimental、慢、貴 | 「完成的定義」很複雜時的實驗 |
| PostToolUse `async: true` 跑測試 | 不擋 Claude 繼續工作 | 結果在下一輪才回來 | 測試要跑比較久的專案 |

判斷原則：

1. **能寫成程式的規則，就不要用自然語言。** prompt hook 留給真正需要語意判斷的事。
2. **安全規則 fail-closed，便利規則 fail-open。** 格式化、通知壞掉就算了；「不准刪資料」壞掉要擋。
3. **Stop hook 是「完成的定義」，PreToolUse 是「禁區」。** 前者回答「做完了嗎」，後者回答「可以這樣做嗎」。
4. **hook 本身也是程式，要測。** 用 `echo '<JSON>' | node hook.mjs; echo $?` 在 Claude 外面跑一遍正反例，比在對話裡試快很多。

### 3.4 測試這一層：AI 寫的測試也要審

hook 只會「執行」測試，不會判斷測試寫得好不好。AI 寫測試常見的問題：

- **斷言改弱**：實作過不了，就把 `strictEqual` 改成 `ok`，或刪掉一個 case。
- **把 bug 寫進期望值**：先寫實作再寫測試時，測試只是把目前行為拍照下來。
- **測到實作細節**：只要重構就整片紅，久了大家就不信任測試。

對策：

- **測試先寫、先看它紅**（RED → GREEN）。測試由你審過再讓它寫實作，實作階段**不准改測試**（可以用 PreToolUse 把 `test/` 的編輯設成 `ask`）。
- **用 `git diff test/` 審斷言**：看有沒有被刪、被放寬。這一步是人做的，也是本週練習的重點。
- **手動 mutation test**：故意把實作改壞一行（例如 `+ 6` 改成 `+ 5`），測試有沒有紅？沒紅代表測試沒有保護到那一行。社群的 TDD skill 也開始把 mutation gate 放進流程（[claudeskills.info: agent-studio/tdd](https://claudeskills.info/zh-hant/skills/oimiragieo/agent-studio/tdd/)，社群內容）。

### 3.5 在 Claude Code 工作流程中怎麼用

一個實用的組合（以 Node 專案為例）：

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "node \"${CLAUDE_PROJECT_DIR}/.claude/hooks/guard-paths.mjs\"",
            "onFailure": "block"
          }
        ]
      }
    ],
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "node \"${CLAUDE_PROJECT_DIR}/.claude/hooks/verify.mjs\"",
            "timeout": 120
          }
        ]
      }
    ]
  }
}
```

- `guard-paths.mjs`：從 stdin 讀 JSON，取 `tool_input.file_path`（官方文件說 Write／Edit／Read 的路徑一定是絕對路徑），落在禁區就 exit 2，落在測試資料夾就回傳 `permissionDecision: "ask"`。
- `verify.mjs`：`stop_hook_active` 為 true 且上次已失敗過時要小心處理；跑測試和產物比對，失敗時把**精簡過的**錯誤訊息寫到 stderr 並 exit 2（整份測試輸出丟回去會吃掉 context）。
- 用 Node 寫 hook 而不是 bash + jq：Windows 和 macOS 都能跑，也不用擔心 `jq` 沒裝（`jq` 沒裝正是 fail-open 最常見的原因）。
- 搭配 subagent：可以在 `.claude/agents/test-reviewer.md` 定義一個 `model: haiku` 的審查 agent，專門跑 `git diff` 檢查測試有沒有被改弱。便宜到可以每次都跑。

## 4. 🏋️ 週末實作（約 45 分鐘）：替 badminton-expense 裝上「完成的定義」

**素材**：`badminton-expense`。我先讀過程式碼：`src/Logic.js` 是純函式（`parseLine`、`resolveDate`、`wednesdayOf`…），`npm test` 目前 11/11 通過；改程式流程是「改 `src/` → `npm test` → `npm run build` 產出 `dist/Code.gs`」，而 `dist/Code.gs` 是手動貼到 Apps Script 的那份。**最容易出錯的地方正是「改了 src 忘了 build」和「直接改 dist」**：貼上去的程式跟測過的程式不一樣。我實測目前 `dist/` 與 `src/` 是同步的。

> 在你自己電腦上的 badminton-expense 做，先開一個分支：`git switch -c practice/hooks`。週報不會動你的 repo。

**目標**

1. PreToolUse 守門：不准直接改 `dist/`；改 `test/` 要先問你。
2. Stop 驗收：測試沒過或 `dist/Code.gs` 沒跟上 `src/`，Claude 就不能說完成。
3. 用「測試先行」加一個小功能，並親手審查 AI 寫的測試。

**步驟**

**Step 1｜寫兩個 hook（約 15 分鐘）**：貼給 Claude Code：

```
在 badminton-expense 建立 Claude Code hooks，全部用 Node 內建模組寫（我在 Windows，不要用 bash 或 jq）：

1. .claude/hooks/guard-paths.mjs（PreToolUse，matcher "Edit|Write"）
   - 從 stdin 讀 hook JSON，取 tool_input.file_path（絕對路徑）。
   - 路徑在專案的 dist/ 底下：stderr 寫「dist/ 由 npm run build 產生，請改 src/ 後重新 build」，exit 2。
   - 路徑在 test/ 底下：stdout 印 JSON，hookSpecificOutput.permissionDecision 設 "ask"，
     permissionDecisionReason 寫「修改測試需要人工確認」，exit 0。
   - 其他路徑 exit 0、不輸出。
   - 這個 hook 設 "onFailure": "block"。

2. .claude/hooks/verify.mjs（Stop）
   - 跑 npm test；失敗時只把失敗的測試名稱和前 30 行錯誤寫到 stderr，exit 2。
   - 用和 package.json build 腳本相同的檔案順序，在記憶體裡組出預期的 Code.gs，
     跟 dist/Code.gs 比對；不一致就 stderr 寫「dist/Code.gs 沒有更新，請執行 npm run build」，exit 2。
     不要自己改寫 dist/Code.gs。
   - 讀 stdin 的 stop_hook_active，在 stderr 訊息裡註明是第幾次被擋，避免無限迴圈時看不出來。
   - timeout 設 120 秒。

3. 寫進 .claude/settings.json。

4. 在 .claude/hooks/README.md 寫出：每個 hook 的用途，以及我可以在終端機用
   echo '<json>' | node .claude/hooks/guard-paths.mjs 手動測試的三組範例輸入（dist、test、src）。

先不要改 src/ 或 test/。
```

**Step 2｜在 Claude 外面測 hook（約 5 分鐘）**：照 README 的範例自己跑，確認 exit code：

- `dist/Code.gs` → `2`
- `test/logic.test.js` → `0`，且 stdout 有 `"permissionDecision":"ask"`
- `src/Logic.js` → `0`，沒有輸出
- 再故意餵一個壞掉的 JSON（例如 `echo 'oops' | node …`），看腳本 exit 什麼。如果是 `1`，在沒有 `onFailure: "block"` 的情況下就會放行，這正是我們加 `onFailure` 的原因。

**Step 3｜測試先行加功能（約 15 分鐘）**：功能是「記錄時第一個字可以寫『上週』，日期就是上週的週三」。分兩次貼：

```
新功能：parseLine 支援「上週 Abby Ellen」，日期取上週的週三（也就是 wednesdayOf(today) 往前 7 天），
explicitDate 為 true。先只在 test/logic.test.js 的「解析一行」測試裡新增斷言，
包含：today 是週六、週日、週一各一個例子，以及「上週 $150」（沒有人名）要回 error。
不要改 src/。寫完執行 npm test，讓我看到新的斷言是紅的。
```

（改 test/ 時會跳出確認，這就是 Step 1 的 `ask` 在運作。）**先自己審測試**再按允許，接著貼：

```
測試我審過了。現在只改 src/Logic.js 讓測試通過，不准修改 test/ 底下任何檔案。
完成後執行 npm run build。
```

觀察：如果它忘了 build 就想結束，Stop hook 應該會把它擋回去。

**Step 4｜審查 AI 產出（約 10 分鐘，這步最重要）**

1. `git diff test/`：這次新增的斷言有沒有涵蓋週一的邊界？（`wednesdayOf('2026-10-05')` 是 `2026-10-07`，所以週一的「上週」應該是 `2026-09-30`，不是 `2026-09-23`，自己算一次對不對。）有沒有任何既有斷言被刪掉或放寬？
2. 手動 mutation：把你寫的 `-7` 暫時改成 `-6`，跑 `npm test`，必須變紅；改回來。再把 `wednesdayOf` 裡的 `+ 6` 改成 `+ 5`，確認既有測試也會紅。哪一個沒紅，就代表那一行沒有被測試保護。
3. 讀 `verify.mjs`：它真的有比對 `dist/Code.gs`，還是只跑了 `npm test`？把 `dist/Code.gs` 加一個空行，對 Claude 說「好了嗎？」，看 Stop hook 會不會擋。

**完成後怎麼驗證**

- [ ] 三組手動輸入的 exit code 與預期一致
- [ ] Claude 想改 `dist/` 時被擋，訊息叫它改 `src/`
- [ ] 改 `test/` 時跳出確認
- [ ] 新功能測試先紅後綠，`npm test` 全過，`dist/Code.gs` 與 `src/` 同步
- [ ] 兩個 mutation 都讓測試變紅
- [ ] 回答：這組 hook 哪一個該 fail-closed？哪一個 `onFailure` 根本不會生效？（答案在 3.2）
