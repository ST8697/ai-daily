## 1. 🛠️ Claude Code 更新

npm 上 10/14 發布了 **2.1.299**（台灣時間 08:23）和 **2.1.300**（22:27）（[CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)、[npm](https://www.npmjs.com/package/@anthropic-ai/claude-code)）。兩版加起來超過 200 條，以下只挑會影響日常使用的。

### 2.1.299

- **Idle compaction**：在終端機裡，超過 200K token 的對話閒置約 54 分鐘後，會在 1 小時的 prompt cache 過期前先自動 compact，這樣你回來發下一則訊息時，就不用把整段對話重新算一次。`CLAUDE_CODE_IDLE_COMPACT_MIN_TOKENS` 可以調整 200K 的門檻，settings.json 設 `"idleCompaction": false` 可以關掉。
  - **我可以怎麼用**：午休或開會前，長 session 可以直接放著，回來比較省額度。但 compact 會丟掉細節，如果你回來要接著做需要精確上下文的工作（例如逐行比對 diff），就調高門檻或關掉這個功能。
- **Windows hooks 改成 fail-closed**：PreToolUse 和 PermissionRequest hook 如果沒有指定 shell、機器上又沒裝 Git for Windows，以前執行失敗會**直接放行**，現在會擋下。
  - **我可以怎麼用**：你在 Windows 上用 Claude Code，如果有用 hook 擋危險指令（W41 週報教的那種），升級後到沒裝 Git Bash 的機器上試一次，確認 hook 真的有在執行。以前你可能以為有保護，其實沒有。
- **MCP allow 規則變嚴格**（breaking）：`mcp__a` 不再同時放行名叫 `a__b` 或 `a_` 的 server，要寫完整的 `mcp__<server 名稱>__*`。agent 的 `tools:` 清單也一樣。
  - **我可以怎麼用**：升級後如果某個 MCP 工具突然每次都要問權限，就是這個原因，打開 settings.json 把規則改成完整名稱。
- **`CLAUDE_CODE_DISABLE_FILE_MENTIONS`**：設定後，`@檔案` 只會把路徑交給 Claude，讓它自己用工具讀，不會把整個檔案塞進 context。很適合 lock 檔、大型 JSON、log 這類檔案。今天的動手練習會用到。
- **`/usage` 新增警告**：max effort、workflows、always-on context（CLAUDE.md、skills、MCP 工具說明這類每輪都會送出的內容），還有過大的 tool 輸出，都會在 `/usage` 標出來。
- **`UserPromptSubmit` hook 改成在 skill 或自訂 slash command 展開之前執行**：hook 擋下 prompt 時，command 裡內嵌的 shell 指令也不會執行。以前 hook 擋了，內嵌的指令可能已經跑完了。
- **Plan mode 修正**：以前 PreToolUse hook 回傳 allow 的寫入動作，在 plan mode 裡還是會被執行。現在 plan mode 不會再寫入。
- **編碼保護**：Write 不再把 Windows-1252、Shift-JIS、GBK、UTF-16BE 的檔案默默轉成 UTF-8（改成拒絕寫入），Read 也修好了帶 BOM 的 UTF-16LE。C#/.NET 的舊專案常有非 UTF-8 檔案，這個修正延續了 [10/12 提到的 Big5 修正](2026-10-12.md)。
- **其他資安修正**：結束時印出的 resume 指令改用 session ID，不再用 session 名稱，避免名稱裡藏的指令在你貼上時被執行；macOS sandbox 修正了透過 symlink 讀寫被禁止路徑的問題；`/ultrareview` 上傳失敗時，不再建議你執行可能把 `.env` 加進 git 的 `git add .`。

### 2.1.300

- **Agent hook 的 `model` 欄位終於有作用**：`haiku` 這類別名現在可以正確解析，subagent 的 model 不會再蓋掉它；指定的 model 不能用時，會改用呼叫端的 model，**而不是直接放行**。如果你有用 agent 型 hook 做把關，這一版之後才算真的可靠。
- **SessionEnd hook** 修正：有背景指令還在跑時離開，SessionEnd hook 有時不會執行。
- **OpenTelemetry**：`api_request` 事件把 cache 寫入拆成 5 分鐘和 1 小時兩種；trace span 加上 GenAI semantic convention 屬性。有在追蹤團隊花費的人可以看出 cache 的成本分布。
- 修正 `ENABLE_TOOL_SEARCH=auto` 在 resume 後 MCP 重新連線時被關掉的問題。

## 4. 💡 開發者應用：在 Claude Code 裡自己做「草稿＋審查」

HydraFusion 的兩個流程，其實就是兩個可以在 Claude Code 裡手動實作的工作模式：

| 模式 | 做法 | 適合 |
|---|---|---|
| **Cascade**（先做、再判斷要不要修） | 便宜的模型先完成 → judge 檢查 → 有問題才請強模型修 | 大量、規則明確的小改動（改文案、補測試、重新命名） |
| **Critique**（多個審查者看實際檔案） | 一個模型寫 → 好幾個 critic 平行審查實際 diff | 會動到金額計算、權限、資料格式的改動 |

在 Claude Code 裡的做法：

- **Cascade**：在 `.claude/agents/` 建一個 `model: haiku` 的 subagent 負責草稿（[10/9 早報](2026-10-09.md)提過 Haiku 5.5 價格是 Opus 的 1/10），主對話用 Opus 只做最後審查。重點是 judge 要**看實際檔案和測試結果**，不是看 subagent 自己寫的總結。這也是 HydraFusion 這次改進 Critique 的方向：用工具看 workspace，不讀文字摘要。
- **Critique**：請 Claude「開 3 個 subagent 平行審查這個 diff，一個看邊界值、一個看權限、一個看資料相容性，每個都要跑 `git diff` 和相關測試，不要只看我的描述」。今天的審查題就是這種情境：兩個 bug 都要看「改了之後的資料」才找得出來。
- **2.1.300 的修正很重要**：agent 型 hook 的 `model: haiku` 以前可能沒有生效。如果你用 hook 做自動 judge，升級之後再確認一次它用的是哪個模型。

## 6. 📖 今日一詞：Prompt cache TTL（提示快取存活時間）

- **定義**：API 把你送出的 prompt 前段（system prompt、工具說明、之前的對話）快取起來，下一次請求的前綴相同時，直接讀快取，不用重新計算。TTL 是快取能保留多久，Anthropic API 有 5 分鐘和 1 小時兩種。
- **運作原理**：寫入快取比一般 input 貴一點，讀取快取則便宜很多（大約一般 input 的十分之一）。只要前綴完全相同、沒有過期，每一輪都只需要付新增部分的全價。**過期之後**，下一則訊息要把整段對話以「寫入快取」的價格重新送一次。200K token 的對話，這一下就很可觀。
- **例子**：Claude Code 2.1.299 的 idle compaction 就是在 1 小時 TTL 過期前（約 54 分鐘），先把對話壓成摘要，所以你回來時要重新寫入的只有摘要，不是 200K 的完整對話。2.1.300 在 OpenTelemetry 裡把 5 分鐘和 1 小時的 cache 寫入分開記錄，就是讓你看得出這筆費用花在哪裡。實務上也可以這樣用：**不要在長對話中途改 CLAUDE.md 或切換 MCP server**，因為前綴一變，快取就全部失效。

## 8. 🔍 審查題

下面是請 AI「把 loan-tracker 的 `addRecord_` 和 `editRecord_` 合併成一個函式，減少重複」後得到的版本。看起來很整齊，也保留了原本的註解風格。請找出其中 2 個 bug（提示：想想「修改」和「新增」在金額檢查上有什麼不同，以及被軟刪除的紀錄）。

```js
/** 新增或修改一筆（p.id 有值就是修改）。呼叫端需持有 lock。 */
function saveRecord_(p, member, hasPayees) {
  const s = summary_();
  if (p.amount > s.remaining) {
    return { error: '金額 ' + money_(p.amount) + ' 超過剩餘待還 ' + money_(s.remaining) + '，請重新輸入。' };
  }
  const sh = sheet_(SHEET.RECORDS);
  if (p.id) {
    const old = findActiveRecord_(p.id);
    if (!old) return { error: '找不到 #' + p.id + '（可能已被刪除）。' };
    const reask = hasPayees && (old.amount !== p.amount || old.date !== p.date);
    const rec = { id: p.id, date: p.date, amount: p.amount, note: p.note, by: old.by,
                  receipt: reask ? RECEIPT.PENDING : old.receipt };
    sh.getRange(old.row, 2, 1, 3).setValues([[rec.date, rec.amount, rec.note]]);
    if (reask) sh.getRange(old.row, 8).setValue(rec.receipt);
    audit_(member, '修改', p.id, recordText_(old), recordText_(rec));
    return { before: old, record: rec, reask: reask };
  }
  // 編號 = 目前筆數 + 1
  const id = s.recs.length + 1;
  const rec = { id: id, date: p.date, amount: p.amount, note: p.note || '', by: member.name,
                receipt: hasPayees ? RECEIPT.PENDING : '' };
  sh.appendRow([id, rec.date, rec.amount, rec.note, member.name, new Date(), '', rec.receipt]);
  audit_(member, '新增', id, '', recordText_(rec));
  return { record: rec };
}
```

背景：`summary_().recs` 來自 `activeRecords_()`，只包含**沒有被刪除**的紀錄；刪除是軟刪除，在「狀態」欄寫入「已刪除」，資料列還在。

## 9. ⚠️ 風險與辨識：tensorlake 惡意版本「帶著合法的 provenance」，GitHub 推出 Actions lockfile

跟進 [10/14 早報](2026-10-14.md) 的 tensorlake 蠕蟲事件。多家資安廠商的分析指出（[Cloud Security Alliance](https://labs.cloudsecurityalliance.org/research/csa-research-note-tensorlake-shai-hulud-ai-sdk-supply-chain/)、[OX Security](https://www.ox.security/blog/shai-hulud-here-we-go-again-tensorlake-npm-package-hit-with-malware/)、[Endor Labs](https://www.endorlabs.com/learn/tensorlake-npm-package-compromised-by-shai-hulud-in-latest-software-supply-chain-attack)；這次都連不上，細節取自搜尋結果，待確認）：**攻擊者先改了專案的 main branch，再讓原本的 GitHub Actions pipeline 正常發布**，所以惡意的 0.5.144 帶有合法的 build provenance。0.5.144 已經從 npm 移除。

這代表「有 provenance 簽章」只能證明「這是從那個 repo 的 CI 建出來的」，**不能證明那份程式碼是安全的**。同一天 GitHub 推出兩個相關的防護：

- **Actions workflow lockfile**（10/14 公開預覽，[GitHub changelog](https://github.blog/changelog/2026-10-14-github-actions-workflow-lockfiles-in-public-preview)）：用 `gh actions-lock` 擴充套件產生 `.github/workflows/actions.lock`，把 action、間接依賴和 reusable workflow 都固定到 commit SHA。這樣即使某個 action 的 tag 之後被攻擊者移到惡意 commit，你的 workflow 還是跑你審查過的那一版。Dependabot 升級 action 時會一併更新 lockfile；管理員可以開「Require lockfile」政策。Free、Team、Enterprise Cloud 都能用。
- **Secret scanning 預設擋 Anthropic API key**（10/13，[GitHub changelog](https://github.blog/changelog/2026-10-13-secret-scanning-blocks-anthropic-keys-by-default-adds-salesforce)）：有開 secret scanning 的 repo（包含免費的 public repo），push 時遇到 `anthropic_service_api_key`、`anthropic_user_api_key` 會被擋下。

**辨識重點**：

- 請 AI 寫 GitHub Actions 時，它通常會寫 `uses: actions/checkout@v4` 這種 tag。**請它改成 commit SHA，或用 lockfile**，tag 是可以被移動的。
- 你的 price-tracker 是 public repo，以後如果加了 Actions 或在任何地方用到 Anthropic API key，push protection 會擋下；**被擋時不要按「允許 push」**，而是把 key 移到 secrets。
- 蠕蟲 commit 的作者是 `claude@users.noreply.github.com`，加上 CI 會自動發布，就形成「看起來是 AI 寫的 commit → 自動發布 → 帶合法簽章」的完整鏈條。main branch 的保護規則（必須經過 PR 審查）才是最前面的那道防線。

**Bug 1：修改時的金額檢查沒有把原本的金額加回去**
- 原本的 `editRecord_` 用的是 `s.paid - old.amount + p.amount > s.cfg.total`：修改後的總還款不能超過借款總額。AI 合併時，新增和修改共用了 `p.amount > s.remaining`。
- 情境一：借款已經全部還清（`remaining = 0`），你發現最後一筆的日期打錯，想改日期、金額不變，卻會被擋下「超過剩餘待還 $0」。
- 情境二：還剩 $10,000，你要把一筆 $20,000 改成 $25,000（實際總額只多 $5,000，完全合法），也會被擋，因為 25000 > 10000。
- 另外，原版 `addRecord_` 在 `remaining <= 0` 時會回「🎉 借款已全部還清」，合併後這個訊息也不見了，使用者只會看到「超過剩餘待還 $0」。

**Bug 2：編號用「有效筆數 + 1」，刪除過紀錄後會產生重複編號**
- `s.recs` 只包含沒刪除的紀錄。假設有 #1、#2、#3，刪除 #2 後有效筆數是 2，下一筆新增的編號是 **3**，跟現有的 #3 重複。
- 之後「修改 #3」或「刪除 #3」時，`findActiveRecord_` 會在兩筆 #3 中找到排序後的第一筆，可能**改到或刪掉錯的那筆**；收款人確認入帳的也可能是另一筆。異動紀錄裡也無法分辨是哪一個 #3。
- 原版用 `getRecords_()`（包含已刪除的）取最大編號再加 1，所以刪除過的號碼不會被重複使用。

**加分（不良設計）**：
- 一個函式用 `p.id` 有沒有值來決定是新增還是修改，呼叫端少傳或多傳一個 `id`，行為就完全不同。權限檢查（`canRecord_` 和 `canModify_`）本來就不同，合併後很容易在呼叫端搞混。原本兩個函式其實沒有很多重複，不值得合併。
- 修改時 `note: p.note` 沒有像新增一樣加 `|| ''`，`p.note` 是 `undefined` 時試算表會寫入空值，`recordText_` 雖然能處理，但跟新增的行為不一致。

**怎麼防**：請 AI「合併重複程式碼」時，要求它先列出兩個版本**所有不一樣的地方**（驗證條件、錯誤訊息、編號規則），每一點都說明合併後怎麼保留。看 diff 時，被刪掉的檢查條件比新增的程式碼更值得看。
